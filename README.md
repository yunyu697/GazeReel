# GazeReel · 凝影

> 目光所及，皆是片库。

把手机塞进纸盒（Cardboard）就能看的 VR 播放器。不是电影点播应用——主要内容是**用户自己拍的片子**：
`VID_20260712_143022.mp4`、`GOPR0231.MP4` 这种无片名、同前缀成百上千、按文件夹和拍摄时间组织的自拍与相机片段，
混着 2D / 180 / 360 / SBS / TAB。

- 包名 `com.gazereel.vr`，Android 8.0+（minSdk 26）
- 片源：本地 / SMB2-3 / WebDAV / HTTP / DLNA
- 播放器：Media3 ExoPlayer + 自绘球面 / 半全景 / 2D 银幕网格

## 安装

**正式版之前不发布安装包。** 包里一律在本地生成：

```bash
./gradlew :app:assembleDebug
adb install -r app/build/outputs/apk/debug/GazeReel-*.apk
```

产物名带项目名与版本号（例如 `GazeReel-1.0.0-alpha2.apk`），不会出现「一堆 `app-debug.apk` 分不清哪个是哪个」。
名字由 `app/build.gradle.kts` 里的 `androidComponents` 从 `version.properties` 派生，不用手改。

alpha 阶段用固定签名（`keystore/gazereel-alpha.jks`），所以**装过旧 alpha 可以直接覆盖，不用卸载**——
卸载会丢掉片源配置、观看断点和格式记忆。

## 版本号

格式 `<major>.<minor>.<patch>-alpha<N>`，例如 `1.0.0-alpha1`。

| 段位 | 限制 | 说明 |
|---|---|---|
| `major` | 无上限 | 有重大更新时进位 |
| `minor` | **≤ 10** | 满 10 再升就进位到 `major` |
| `patch` | **≤ 10** | 满 10 再升就进位到 `minor` |
| `alpha` | 无上限 | 同一版本内继续迭代就 `+1` |

**合法**：`11.10.10-alpha11`　　**非法**：`1.11.11-alpha1`

段位越界不会「悄悄发出去」：`app/build.gradle.kts` 在配置阶段就会 `check()` 失败，
`tools/bump_version.py --check` 在 CI 里也会拦一道。

### 升版本

唯一真相源是根目录 `version.properties`。**不要手改那一行**，用脚本：

```bash
python3 tools/bump_version.py            # 看当前版本与 versionCode
python3 tools/bump_version.py alpha      # 1.0.0-alpha1 → 1.0.0-alpha2
python3 tools/bump_version.py patch      # 1.0.0-alpha3 → 1.0.1-alpha1
python3 tools/bump_version.py minor      # 1.0.10-alpha2 → 1.1.0-alpha1
python3 tools/bump_version.py major      # 1.10.10-alpha9 → 2.0.0-alpha1
```

`versionCode` 由 `major(1e8) | minor(1e6) | patch(1e4) | alpha` 拼成，
保证单调递增，且正式版（尾段 9000）永远大于自己的全部 alpha。

### 发版

**正式版之前只打 tag，不发包。** tag 只用来标记「代码走到哪一步了」，安装包始终在本地生成。

```bash
python3 tools/bump_version.py alpha
git add version.properties && git commit -m "chore: 版本升到 1.0.0-alpha2"
git tag v1.0.0-alpha2
git push && git push --tags
```

tag 会触发 CI：校验 `tag == v + version.properties`（不一致直接失败）、跑结构校验、编译一遍证明能构建。
**它不上传任何产物**——构建通过 ≠ 有包可装，要装请本地 `assembleDebug`。

## 本地构建

```bash
# 需要 JDK 17 与 Android SDK（compileSdk 35）
python3 tools/check_structure.py          # 结构校验，秒级
./gradlew :app:assembleDebug              # 产出 app/build/outputs/apk/debug/GazeReel-<版本>.apk
./gradlew -q :app:printVersion            # 打印当前版本号
```

Cardboard SDK 以本地 aar 形式随仓库提供（`app/libs/cardboard-sdk.aar`），CI 不需要额外下载。
不放这个 aar 也能编译，只是会退回纯传感器实现。

### 没有片源怎么验

六段带方位色标的测试片，一条命令生成（需要 `ffmpeg`，产物在 `../output/testclips/`，不入库）：

```bash
python tools/make_testclips.py     # 360 / 180SBS / 2D / 鱼眼圆 / 鱼眼全画幅 / 未缝双鱼眼
python tools/check_testclips.py    # 64 条自检：投影公式、锚点取色、交付规格
adb push ../output/testclips/. /sdcard/Movies/
```

每个世界方向一个固定颜色（前=红、右90=绿、左90=蓝、后=黄、上62°=品红、下62°=青），
三种投影画的是同一套角度图案，所以「换了投影还对不对」也能直接比。
判读口诀与每段证明哪一项，见 [`docs/TESTCLIPS.md`](docs/TESTCLIPS.md)。

### 真机验收：一条命令

手机塞进纸盒之后没法翻页，所以「放指定的那一部片」由命令点名：

```bash
bash tools/verify_device.sh            # 装包 → 推片 → V1..V9 逐项起播 → 截图 + 日志切片 → 记录表
bash tools/verify_device.sh V4 V5      # 只跑两项
bash tools/verify_device.sh --list     # 看项号对应哪段片
```

它只保证「放的是那一部片、证据按项存好了、没起播立刻报错」；
**合格与否仍要人眼看**——判据见 [`VERIFY-2.2.0.md`](VERIFY-2.2.0.md)。

## 先判断我的片子是什么格式

不知道片子是什么格式，不用装工具。最快是两步：先看分辨率数字，再看画面长相，照着下表对号入座。

| 分辨率 / 画面长相 | 大概是 |
|---|---|
| `1920×1080` / `3840×2160`，普通横屏一个画面 | 2D 平面 |
| 画面里左右并排两个几乎一样的小画面 | SBS（左右 3D） |
| 画面里上下叠着两个几乎一样的小画面 | TAB（上下 3D） |
| `3840×1920` / `4096×2048` / `5760×2880`，2:1 的长条 | 二义：360 Mono（一整幅）或 180 SBS（左右两半）；看画面是不是被竖着劈成左右两半 |
| `5400×2700` 的 SBS（每眼 `2700×2700`，1:1） | 180 SBS |
| `2700×2700`（1:1，单幅） | 180 Mono |
| 一个圆形鱼眼（`MKX200` / `MKX220` / `VRCA220` / Canon RF5.2 的每只眼），圆外是黑的 | **鱼眼镜头 · 圆形**（支持，见下） |
| 整幅铺满、四角没有黑边，画面越靠边拉得越开（单反/微单装鱼眼、机内裁切） | **鱼眼镜头 · 全画幅**（支持，见下） |
| `5800×2900` 双鱼眼并排、两个圆各是**前后方向** | 未缝合双鱼眼 360，本工程**明确不支持**（会提示，不打弯画面） |

再看来源：Insta360 / GoPro MAX 这类全景相机多为 360；VR180 相机 / Canon 双鱼眼镜头多为 180；手机、运动相机、普通摄像机拍的基本都是 2D。

**文件名写的不一定准。** 真机实测片库里标着 `_4K_HEVC_` 的片子，实际编码是 VP9 / H.264。判断只信画面与容器信息，别信名字里的「4K」「HEVC」字样。

**220 / 270 看画面分辨不出来**：都是等距柱状的长条展开图，跟 180 长得很像，只能靠压制方说明或文件名标记。别自己猜 220 / 270，猜错张角会把内容压歪。

**鱼眼是唯一「一眼看得出」的一种**：画面里是一个圆（或左右两个圆），圆外是黑的。看到圆就选鱼眼，再从设置第 2 页挑镜头预设（180 通用 / 190 RF / 200 MKX / 220 VRCA）；如果圆的边缘没贴到画面边（有黑边），把「鱼眼画面圆」往下调，直到圆的边缘正好落在采样边界上。

**先分清鱼眼的两种画幅**，选错了怎么调都不对：

| 你看到的 | 画幅形态 | 怎么处理 |
|---|---|---|
| 一个完整的圆，圆外黑 | **圆形**（默认） | 张角选镜头型号；圆没贴边就把「画面圆」调小 |
| 整幅都是画面，四角没有黑边，越靠边越拉伸 | **全画幅** | 打开「鱼眼全画幅」开关，此时「画面圆」不计 |

区别的物理来源：VR180 相机 / MKX / VRCA 的传感器比镜头成像圈大，所以能看到完整的圆；单反微单装鱼眼镜头时机身把圆裁掉了，四角就是画面的一部分。全画幅的标称张角（180°/200°）是**对角线**张角，程序按半对角线归一，四角正好落在圆边。

**「鱼眼画面圆」是占短边的百分比**：圆形鱼眼的那个圆在像素里必须是正圆，所以它只可能受**短边**限制。单眼方片（VR180 规范的 SBS，每眼 1:1）100% 就是圆贴满；单眼 2:1 的片子（圆在中间、两边黑）程序会**按短边自动补偿**，不用你手动填 50%。补偿状态写在设置第 2 页上（如「眼画幅 2.00:1 · 按短边补偿，圆不会拉扁」），对不上再调画面圆。

**镜头上限认不出就选最接近的预设**：`MKX220` 选「220 VRCA」（同为 220°），`MKX200` 选「200 MKX」；RF5.2 的两只眼选「190 RF」。预设只改张角与画面圆，不影响「这片是不是鱼眼」——那是格式说了算。

**这四项戴镜前就能定**：手机端「设置」里有一节「画面与鱼眼」—— 2D 银幕宽度、球面画面缩放、鱼眼张角、鱼眼画面圆、画幅形态（圆形 / 全画幅），外加四个镜头预设。它和 VR 内设置第 2 页写的是同一份配置，谁先改谁生效。

**未缝合的双鱼眼 360 会被明确拒绝**：Insta360 / Gear360 这类机内原始片（`.insv` 等）画面里也是两个圆，但那是**同一只眼的前后两支镜头**，不是左右眼。本工程按「一只眼一个圆」解，每只眼只看得到一个圆、前后方向还错位——所以这类片子会先弹一张说明卡，然后把画面按 2D 银幕原样放着（能看见里头有什么，但不做任何假变换）。要正常看，先用相机 App（Insta360 Studio 等）或 `ffmpeg -vf v360=` 缝成等距柱状 360，缝完就是普通的 360 片源。

拿不准就别乱命名：留空让应用弹「确认视频格式」浮层，戴镜后照着画面选。十项是 360° Mono / SBS、180° SBS / TAB、220° Mono / SBS、270° Mono / SBS、2D Mono / SBS，其中 220 / 270 各有 Mono 与 SBS 两档。选错不用改文件，手选结果会按片记住。

## 视频命名规则（格式识别）

命名是最硬的一条判据：优先于容器元数据与画幅比猜算，名字写了视场就直接按它播。

**标记必须是独立词**：被 `_` `-` 空格 方括号等分隔开才认。大小写不敏感，`SBS` 与 `sbs` 一样。`1080p` / `IMG_1801` 不会被误判成 180 —— 数字要独立成词，前后不能挨着别的数字。

`Trip_180_SBS.mp4` 能完整识别；`Trip180SBS.mp4` 这种粘成一团的**不可靠**：立体布局 `sbs` 必须作为独立词才认得，但视场数字走的是另一条「数字边界」规则，`trip180sbs` 里的 `180` 仍可能被认出来 —— 结果会变成「180 Mono」而不是 180 SBS，左右两幅不分开。所以宁可多打两个下划线。

可认的词表：

| 类别 | 标记 |
|---|---|
| 视场 180 | `180` `180x180` `vr180` `180vr` `fov180` `180sbs` `180tb` `180°` |
| 视场 360 | `360` `360x360` `vr360` `360vr` `fov360` `360sbs` |
| 视场 220 | `220` `pano220` `fov220` `220sbs` `220tb` `vr220` |
| 鱼眼（单镜头） | `fisheye` `fish` `mkx200` `mkx220` `vrca220` `rf52` `鱼眼` |
| 未缝合双鱼眼 360（**硬证据，一定拒绝**） | `dfisheye` `dualfisheye` `insv` `unstitched` `双鱼眼` `前后鱼眼` |
| 同一类，但只有**品牌线索**（没有 `360`/`equirect` 才拒） | `insta360` `gear360` `onex2` `onex3` `onex4` |
| 视场 270 | `270` `pano270` `fov270` `270sbs` `270tb` `vr270` |
| SBS 左右 | `sbs` `lr` `hsbs` `halfsbs` `3dh`；`side_by_side` / `side-by-side` / `left_right` / `left-right` |
| TAB 上下 | `tb` `ou` `htab` `3dv`；`over_under` / `over-under` / `top_bottom` / `top-bottom` |
| Mono（别切两半） | `mono` `monoscopic` `2d180` `2d360` |
| 2D 平面 | `2d` `flat` `plane` `screen` |

**品牌名不等于「没缝」**：Insta360 Studio / GoPro Player 导出已缝合的 360 之后，文件名常常还带着
`INSTA360`。所以品牌名只在「名字里没有任何已缝合标记」时才当作机内原片拒绝；一旦出现 `360` /
`equirect` / 容器声明的球面元数据，就按正常 360 播。`.insv` 这类后缀不受此限——它本身就是「没缝」。

**`rf52` 会多问一次**：Canon RF5.2mm 双鱼眼是**镜头型号**。机身原片是两个圆并排（未缝），
而 EOS VR Utility 导出的单眼圆图也可能沿用这个命名，名字分不出来。所以按鱼眼给画面，但要求
确认一次——猜错的代价是整幅变形。**Canon 机身原片（`CRM_xxxx.mp4`，名字里没有 rf52）无法从
命名识别**，会按 2:1 几何当成 180，看到两团圆就是它；改名带上 `rf52` 或手动选鱼眼即可。

`3dh` / `3dv` 只说「是 3D」没说怎么排，算歧义，会再问一次确认。

照着改就行：

```
IMAX_2D.mp4               2D 平面
海边_180_SBS.mp4          180° 左右
海边_180_Mono.mp4         180° 单幅
山顶_360_Mono.mp4         360° 单幅
城市_220_SBS.mp4          220° 左右
海边_鱼眼_SBS.mp4         鱼眼（VR180 双镜头，每眼一个圆）
城市_270_SBS.mp4          270° 左右
```

优先级与回退：

1. 文件名 > 容器元数据（`st3d` / `sv3d` / XMP `GSpherical:`，含裁剪比）> 每眼画幅比（2:1 → 360，1:1 → 180）。
2. 只写了 `sbs` / `tab` 没写视场时，按最常见的 180 兜底（`SBS` → 180 SBS），置信度标为 0.70 表示这是猜的。是否自动播放还要看画幅比自不自洽；拿不准时会弹「确认视频格式」，不会静默播错。
3. 220 / 270 不参与画幅比猜算：每眼约 1.22 / 1.50，离 4:3（1.33）、16:9（1.78）太近，认了会把普通电影判成球面。这两档只认文件名标记或手选。

边界：`mkx200` / `mkx220` / `vrca220` / `rf52` 这类是**鱼眼镜头**（19:0x 起支持单镜头反畸变），不是等距柱状张角档 —— 名字里写 `220` 而不写 `mkx220`，会按 220° 全景播，鱼眼画面会明显扭曲。**未缝合双鱼眼 360**（两个圆并排、各覆盖前后半球）需要两镜头混合缝，本工程明确拒绝：`.insv` / `dfisheye` / `双鱼眼` 这类标记会直接降级成 2D 银幕 + 一张说明卡，不会打歪画面让你以为是片子坏了。立方体 / EAC 是另一套投影，也不支持。识别不了时会弹确认浮层，不会静默播错。
