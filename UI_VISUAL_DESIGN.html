00 / 为什么重做

上一份不是设计

上一版交付的是可用性整改清单：视场角推导、目标最小像素、状态机、文件清单、验收标准。它回答的是「怎么才能不出错」，没有回答「它长什么样」「用起来什么感觉」。好看与顺手都不是工程约束的副产品，得先有立意，再谈尺寸。本文件只谈这两件事；上一版 UI_DESIGN_SPEC.html 降级为方向选定后的实施附录。

01 / 概念

从品牌名长出来的画面

GazeReel 凝影——目光停住，胶片盘开始转。于是界面不该是「一个播放器设置页」，而是走进放映室的过程：手机上是检票与选片，塞进纸盒是熄灯，头显里只剩下银幕和你要看的那部。

01 光

一屏只有一处亮

#67E8F9 不用于装饰，只给「现在该点的那个」。所有次级信息退到 #8FA3BC，背景退到 #070E19。

02 圆

胶片盘母题

按钮是胶囊、进度是环、焦点是圆盘。全界面不出现直角方块，和图标里的两片圆角镜片对上。

03 留白

一次只给一个决定

首屏不放表单、控制台不放二十个按钮。留白不是风格，是替用户把注意力收窄。

04 连续

不跳色、不换语言

手机与头显同底色、同字阶、同圆角。塞进纸盒那一刻，视觉不重新开始。

05 质地

靠排版，不靠特效

层次来自底色阶、字距与比例，不靠投影和描边堆。暗环境里发光边缘会脏，纯色更干净。

光的使用青色面积不超过单屏 5%，只给推荐项、当前焦点、进行中的进度、主 CTA。其余一律退到蓝灰阶。
留白节奏手机端区块间距 24sp、卡片内 12sp；VR 端焦点元素四周至少留出一个自身高度的空区，保证凝视时没有其他东西抢注意力。
动效只用透明度与 8–16px 的垂直位移，缓动 cubic-bezier(.2,.7,.2,1)，120–240ms。控制台从下方浮起、字幕交叉淡入、熄灯过渡 600ms 渐黑。禁止视差、回弹与跟随头部的弹性动画。
反馈凝视进度用目标外沿的环形描边而非独立转圈；确认时目标短暂填实青色 80ms。破坏性操作二次确认，且「取消」比「确认」更容易命中。

05 / 顺手：按真实使用顺序的十个决定

不是「目标多大」，是「这一刻人手里在干什么、眼睛能看到什么、做错了能不能回来」。

时刻设计决定
第一次打开首屏不给表单，给三条路；局域网自动发现是默认推荐。地址输入收进次级页，并附一句「去哪找这个地址」的人话。
输入时边输边校验，示例地址随协议变化；错误文案写清可能原因（同一 Wi-Fi / 设备休眠 / 地址写错 / 凭证不对），不出现错误码。
等扫描不转圈，写「已发现 12 部，还在继续」，可随时停止且已找到的保留。
失败之后地址与凭证就地保留，一键重试；不回首页、不重填。未实现的协议在下拉里就置灰说明，而不是点完才弹提示。
塞进纸盒前新增过渡页：大字对准说明 + 3 秒倒计时 + 可跳过。避免手机还在手上就跳进双眼分屏。
刚戴稳第一屏永远是正前方舒适区的片库，且默认停在上次看的那一部；不需要抬头低头找入口。V2.3 补充：「正前方」不是水平前方，而是当前姿态下的舒适中心（见第 09 章）；躺下后画面要跟过去，不能让人仰头找片库。
找片V2.2 修订，以第 08 章为准。先在手机上按拍摄时间 / 文件夹 / 设备选好一叠，戴镜后第一屏就是这一叠；VR 内不做键盘检索。胶片盘索引轮从「首字母 A–Z」改为月份刻度，摇头一次换一叠而非翻 1 部。V2.1 的「片名搜索 + 待看清单」保留为电影类片源的次要入口，不再是默认路径。
播放中调音量控制台默认不出现，低头或触发键唤出，8 秒淡出，字幕留下。音量交给手机实体侧键，一次一档、零瞄准；亮度默认跟随环境光，手动只有三档大胶囊。任何档位变化在视野中央浮出大字与 5 段条，1.2 秒淡出。不做凝视滑杆、不做要反复瞄准的 ± 按钮。
选错格式确认浮层有明确「返回片库」，改格式不重开片源；自动识别项高亮但永远可以改，不被系统替用户做决定。
想出来任意界面一个动作回到片库，片库一个动作回到手机配置；退出用长按触发键而不是瞄准一个小叉。删除片源、清除格式记忆二次确认。
判断标准很简单：用户能不能在不开灯、不取出手机、不重新学习的情况下，把一部片从头看到尾，中途还能调音量、换片、退出来。

07 / V2.1 增补：把「调」和「找」从脖子上挪走

V2.2 修订：本章 07.1 的省力调节结论继续有效；07.2 的首字母索引轮、按片名搜索、待看清单三项建立在「内容是电影」的前提上，已被第 08 章的按拍摄时间成叠 + 月份刻度取代，仅保留为电影类片源的次要入口。07.3 中「按首字母分段的计数查询」相应改为按月份分段。
V2.3.1 修订（前提错误）：本章所有「亮度默认跟随环境光自动定档」的表述一律作废。手机塞进纸盒后，光线传感器被纸盒与脸完全遮住，读数恒为极暗；躺姿下再叠一层枕头 / 被子，自动亮度会把画面压到最暗。核对源码也确认：全工程只注册了 TYPE_ROTATION_VECTOR，没有任何 TYPE_LIGHT 监听，brightness 是纯手动整数（默认 70）经 uBrightness 生效。改为：环境光只在戴镜前读一次，作为初始档位写进设置；塞进纸盒后冻结，不再自动变化，播放中只保留暗 / 标准 / 亮三个大胶囊。07.3 表里「接入环境光传感器给亮度自动档」相应改为「戴镜前读一次初始亮度」。配置页首屏的「默认跟随环境光」文案改为「戴镜前按环境定档」。

头动只该用来「选」

方向 A 确认后，用户指出两处仍然累人的地方：亮度音量完全靠头的运动做精确调节；影片很多时没有快速找片的办法。这两个问题同根——把连续、高频、要求精度的动作交给了脖子。核对源码也确认了：VrActivity.onKeyDown 已把手机实体音量键接成 VrAction.Adjust("volume", ±1)，但 adjust() 只改写设置值，播放时视野里没有任何反馈；TriggerDispatcher 的长按是返回、双击是打开设置，GestureRecognizer 的点头摇头也已被播控占满，系统里根本没有为连续调节留通道。而 mediaDao().observeAll() 是 ORDER BY title 全量平铺，片库一次只露三张卡、摇头翻 1 部，832 部就要摇 832 次。

07.1 亮度与音量：精确值前移，头显里只留粗档

01 精确值

戴镜前用手指设一次

配置页加一组真实滑杆设定亮度与音量精确值，按片源记忆。手指适合连续精调，脖子不适合。

02 音量

交给手机实体侧键

KEYCODE_VOLUME_UP/DOWN 通道已存在，一次跳一档（静音 / 低 / 中 / 高 / 最大），零瞄准、有肌肉记忆。补的只是 UI 反馈与首次引导。

03 亮度

让「调」变成「不用调」

默认跟随手机环境光传感器自动定档；手动只有暗 / 标准 / 亮三个大胶囊，凝视一次跳一档，没有百分比和小加号。

08 / V2.2 增补：柜子里装的不是电影

三个问题，同一个前提错误

用户评审原话：「不错，确实已经在向好用的方向修改了；但是还不够，比如说检索是以电影为对象的，但如果是用户自己的视频呢？另外要让用户在配载后尽可能不需要手动取下手机，那么 VR 内是不是要提供切换服务器 / 目录的功能？还有 VR 视频的格式是不都支持齐全了，因为还有鱼眼、立方体，甚至 SBS 的 3D 视频是不是也要提供支持？」

这三句不是三个补充需求，是同一个错误的三个切面：前面所有版本都默认 GazeReel 是「电影点播应用」。片名、海报、首字母索引轮、待看清单，全部建立在「内容有片名、有海报、按字母排」这个前提上。而真实的主角是 VID_20260712_143022.mp4、GOPR0231.MP4、MVI_2043.MP4——没有片名、没有海报、几百个同前缀、按 DCIM/Camera/ 和拍摄日期天然成组，还混着 2D 家庭录像、360 相机片段和 SBS 3D。

核对源码后可以确认：这不是「检索方式要改」，而是片库的数据模型里根本没有「用户自己的视频」这个东西。V2.1 那条「头动只用来选」的铁律因此要再进一格。

V2.2 铁律：戴镜后只做「换」，不做「找」和「配」。所有需要命名、输入、逐层浏览、精确判断的事，都在戴镜前替用户做好；头显里只出现「已经整理好的几格」。

09 / V2.3 增补：姿态变了，正前方也该跟着变

先给结论：目前没有自动处理

用户最后确认的问题：「如果用户在配戴之后姿态发生改变，比如坐姿变成躺姿，有没有相应的处理方式呢」。把头追链路从传感器到 UI 查完，答案是：工程里对「人坐着还是躺着」零感知，唯一的手动兜底在躺姿下也基本用不上。

位置现状
SensorHeadsetProvider.start()只注册 TYPE_ROTATION_VECTOR；VrActivity 没有第二个传感器监听，全工程无重力 / 姿态判据。
VrUiState.kt / VrSettings.kt没有姿态、重力、舒适中心或姿势模式字段，VrActivity 的 onResume/onPause 也只管 GL 与播放器。
VrCoordinator.kt:83VrAction.ResetForward -> headset.recenter()：只调一次方法，不回写 uiState、不给任何反馈、不重置手势窗口，用户不知道有没有生效。
VrUiLayer.kt:290入口是设置浮层里 250×46px 的小按钮「重置正前方」，藏在 16 个目标中。躺下后的路径是「双击 → 设置 → 瞄准小按钮 → 确认」，还得先仰头到能看见画面的角度。
GestureRecognizer.kt:83判据是「700ms 内 pitch 往返 ≥10° 判点头 / yaw 往返 ≥15° 判摇头」。从坐到躺 pitch 连续变化 60–90° 且伴随回弹与调整，极可能被误判成点头或摇头，触发播放 / 暂停或切片；onActivity() 还会顺手把控制台唤出来。
SensorHeadsetProvider.headRotation():58viewLocked 时直接 return frozen.copyOf()，而 recenter() 只改 inverseOffset——后者仅在非锁定分支的 Matrix.multiplyMM 里被用到。一旦开启「锁定视角」，躺下后怎么按都重置不了。
VrRenderer.kt:72 / VrUiLayer.kt:78uiQuad(-0.46f) 与 panelCenterY() 把播放控制台固定在世界坐标下方约 13°。躺姿下「下方」意味着朝脚的方向看，脖子并不舒服；这个俯角需要随姿态变。
好消息：底层数学是够的。两个 Provider 的 recenter() 都用 Matrix.invertM(inverseOffset, 0, raw, 0) 取完整旋转矩阵的逆，不是只清 yaw；所以按一次就能把含 pitch / roll 的当前姿态设为新零点，2 米处世界锁定的 UI 平面会跟着新参考系走。缺的是触发时机、反馈、姿态感知与人体工学俯角，不是能力本身。

另有边界要说准：Cardboard 是 3DOF，手机贴在脸上，躺下时眼睛相对手机的位置不变，IPD 与畸变也不变。这纯粹是旋转参考系与 UI 人体工学问题，不是缺硬件、也不需要位置补偿。

09.1 不做「坐 / 躺」两个模式，做舒适中心

半躺、靠沙发、侧躺是连续量，二元模式开关会反复误判。更合适的抽象是「舒适中心」：正前方不由重力或磁北定义，而是「当前稳定姿态下视线的自然落点」。系统只在这个落点持续偏移时，把整个参考系重定一次——视频、UI、字幕、准星作为一个整体走，不分别处理。

姿态与视野参考系 · 躺姿下要重定的是整个参考系，不是让用户把头仰回去

09.2 三层保障：迟钝地感知、先问再动、随时可改

01 感知要迟钝

不碰现有头追链路

V2.3.1 修订：不必注册第二个传感器——SensorManager.getRotationMatrixFromVector() 输出的矩阵已含重力对齐（世界 Z 指天），从现有 headRotation() 的原始矩阵反解重力方向即可，省一个监听、也避免两个数据源时间不同步。判据仍是「新方向稳定 ≥1.5s + 角速度低于阈值 + 与当前基准偏离 >40° + 迟滞带」。低头调纸盒、咳嗽、翻身、侧躺微调都不该让画面动。V2.4 定案：检测结果只用来「提问」，不再直接重定；360 内容里长时间主动抬头因此不会抢走画面。

02 先问再动

检测不等于执行

V2.4 定案：检测到稳定姿态变化后，只在舒适中心浮出一个大目标「姿势变了 · 把正前方挪到这里？」，画面一帧都不动。用户凝视一次才进入 0.8s 缓转；不理它，提示数秒后自行淡去，画面与参考系保持原样。世界锁定 UI 平面整体转过去，屏幕空间准星与字幕不动。

03 零学习成本

不新增手势、不占用触发键

确认用的就是已经学会的「凝视停留」，命中判定与片库里选片完全一致。长按=返回、双击=设置、单击=播放 / 暂停、点头摇头=播控一律不动，也不需要撤销窗口——不确认就什么都不发生。躺姿下够不着触发键不再是个问题。

04 兜底在环境层

不进设置浮层

临时确认浮层与环境层第 5 个大目标「把正前方挪到这里」是同一个控件：自动检测到就浮出来问，用户主动进环境层也能随时重定。单屏仍是 5 个目标，不进设置浮层、不取手机。

环境层 · 左右眼共用同一份 UI；换柜子与重定正前方是同类操作，不该分属两处

时刻通道为什么
重力方向稳定 >1.5s 且偏离 >40°系统只标记候选，舒适中心浮出确认大目标，画面与参考系都不动检测与执行分离，主动注视不会被抢画面

09.3 语义纠正：冻结 ≠ 重定基准

这是躺姿场景最容易搞混、也是当前代码里真实出错的地方。VrSettings.lockView 是「冻结头追输出」，recenter() 是「换参考系」，两者不是一回事，更不能让前者绕过后者。

锁定视角 lockView重定基准 recenter
作用冻结头追，画面钉在锁定瞬间的朝向换参考系，画面随新的正前方重新对齐
躺姿下应临时让位，否则用户被钉在旧朝向凝视确认后触发一次
代码现状headRotation() 返回 frozen只改 inverseOffset，被 frozen 分支绕过 → 失效
修正姿态重定时临时解锁重定后按新基准重新冻结；无论是否 locked 都要生效

12.1 光标必须跟着视线走，而不是钉在画布正中

原来

一个不动的小圈

准星画在 UI 纹理的 (W/2, H/2)，也就是面板正中。可播放控制台的平面在视野下方约 13°，面板正中离真实视线差着十几度——用户看到的是一个「不动的小圈」，只能靠触发临近的按钮去猜，猜错就换片、暂停或退出。

现在

画在视线落点上

由渲染层用 gazePoint() 算出真实落点交给绘制层，光标画在那里。它同时也是一道保护：视线离开面板范围就不画——纯看片时画面正中没有任何东西。

三条例外，都是为了「不影响看片」：设置里关掉就完全不画；没上膛不画（那时凝视本来不生效，画出来只会让人以为坏了）；播放中控制台收起时不画（那一刻用户在纯看片）。设置浮层新增「虚拟光标 · 开/关」，默认开。

与 09.4 / A3 的关系：设计原话是「准星属于屏幕空间层，保持屏幕中心、不参与世界参考系重定」。当前实现仍是画在 UI 纹理上，只是位置改成了真实视线落点——在面板居中时两者等价，面板偏移时不等价（比如控制台下移 −13°，严格意义上的屏幕空间准星应该始终在屏幕正中）。真正的三层拆分仍属 CHECKLIST B6，这一刀没有假装做了。

12.2 控制台的消失与回来

问题原因结论
一直挡在视频上，永不隐藏GazeDetector 在准星落点抖动超过 8px 时调 touch()，把头动当成「操作」。手机塞在纸盒里一直在抖，8 秒静默永远数不完。头动不算操作。只有触发键、实体键、识别到的手势会刷新计时。
连按调节时控制台中途消失touch() 只在「距上次活动超过 1 秒」时更新时间戳。连按间隔都不到 1 秒，时间戳停在第一次按键上。无条件刷新。

13 / V2.15 增补：把「找设备」真的做成找设备

第一轮真机反馈的第一条至今只修了一半：「查找同一 Wi-Fi 下的设备时显示这个 Wi-Fi 下没找到设备，但实际上局域网内有两台 NAS」。V2.12 只把提示改准了（分清「没设备」和「设备没开媒体共享」），两台 NAS 仍然找不到，用户还是得手填 IP。

13.1 为什么「没找到设备」这句话在只开 SMB 的网络里永远是对的

原来

只问 DLNA

发现走 SSDP M-SEARCH，问的是「谁提供 ContentDirectory 服务」。这是媒体服务器的广播，只开共享文件夹的 NAS 根本不在这个协议里，它不会、也不需要应答。所以「没找到」不是网络坏了，是问错了对象。

现在

两条路一起问

SSDP 照旧问 DLNA，同时扫本机所在网段的 445 端口，谁在等 SMB 连接就是一台共享设备。两条并行，总时长还是 SSDP 那 4 秒，不会因为多扫一遍让用户多等。

为什么不是「再发一次广播」：SMB 没有广播发现机制，Windows「网络」里看到的邻居靠的是 NetBIOS 浏览主浏览器，那套东西在纯 SMB2/SMB3 环境里已经不可靠。想在不问用户要任何输入的前提下知道谁开着共享，直接问网络本身是唯一稳的路子。

13.2 扫到之后，还得让它有名字

只给一串 192.168.1.10，用户面对两台 NAS 时还是分不出哪台是哪台。所以扫到之后补一次 NetBIOS 名称查询（NBSTAT）——问到的就是他在电脑「网络」里看到的那个名字。名字拿不到就老老实实显示 IP，不编一个假名字：认错设备比不认设备更糟。

环节做法为什么这样
扫哪些地址本机所在的那一段，最多 254 个；前缀比 /24 宽也只取自己那 254 个找两台 NAS 不需要把整栋楼的地址都连一遍；手机同时开着移动数据时也只会扫 Wi-Fi 那一段。
怎么判活48 路并发连 445，单个 260ms 超时最坏 6 轮、约 1.6 秒。再短会把慢设备漏掉，再长用户会觉得卡住。
名字NBSTAT 查一次，350ms 超时，失败即放弃名字是锦上添花，不能因为它让设备从列表里消失。
重名两台都叫「NAS」时才在后面补 IP名字本身有价值，不该每台后面都拖一串数字。

13.3 点下去之后：能进就直接选文件夹，不能进就只让他补账号

访客能进

直接进选共享

不少 NAS 开着访客访问。先用空账号试一次，进得去就把共享列出来，用户点一个共享、再点一个文件夹，保存。全程没有输入框。

要账号

只补账号密码

空账号被拒时，IP 和类型已经替用户填好了，表单自动展开、焦点落在账号那一格。他要做的只有填自己知道的那两样。

三种结果给三种下一步，不再用一句「没找到设备」糊过去：

扫到了什么界面说什么下一步
媒体服务器 + 共享设备找到 N 台设备一个列表，服务器点一下直接进；共享设备会问账号
只有共享设备它们只开了共享文件夹，没有开媒体服务器点一台，选好文件夹就加上了
什么都没扫到回了广播的台数 / 真的没找到两者分开讲，然后展开手动添加兜底

13.4 这一章明确没做

① 只扫 /24：企业网 /16 或跨 VLAN 的场景扫不到，仍需手填 IP；② 只看 445：只开 139（老设备）的共享不会出现在列表里；③ 不做 mDNS / Bonjour 发现，群晖的 .local 名字用不上；④ NBSTAT 报文与端口扫描都没在真机网络上跑过，只经过静态推演与编译——真机第一件事是确认「两台 NAS 是否出现在列表里」「名字是不是用户认得的那个」。

14 / V2.16 增补：名字、共享列表、回到播放与成叠

alpha5 真机反馈四条：两台 NAS 能找到但只显示 IP；之前那个 IP 仍然「设备没有返回共享列表」；播放中调出片库之后没有回到播放的路；另外要求别再只修 bug，同时往前推进。前两条都是我的实现错误，不是设备不支持。

14.1 名字为什么显示成 IP

原因

NetBIOS 名字是 OEM 编码

NBSTAT 应答里的名字是 15 字节 OEM 编码：中文名在中文 NAS / Windows 上是 GBK。我按 US-ASCII 解，一个中文名变成一串 ?，被名字校验一拒，就退回显示 IP。

现在

先按 GBK 解，再按 UTF-8

GBK 能正确解出纯 ASCII 名，所以先试它；解出替换字符就换下一个。再加一道反向 DNS 兜底（只等 400ms，拿不到就当没有）。都没有才显示 IP——不编名字。

14.2 「设备没有返回共享列表」的真正原因

V2.12 我把这条归因为「设备不支持 srvsvc」，然后写了 40 个常见共享名做兜底。真机又试了一次，仍然是这句话。这次回源码逐字节核对报文，找到的是我自己的编码错误。
环节上一版写的为什么是错的
NDR 排布ServerName 的字符串紧跟在它的引用号之后，再写 Level / EntriesRead / BufferNDR 把所有定长字段排在前面，变长内容统一延后。服务器在 Level 那个位置读到的是字符串的第一个 DWORD，整条报文被判为畸形请求——设备当然「没有返回共享列表」。
定长部分7 个字段顺序混乱，TotalEntries 少了一个引用号按 IDL 展开 SHARE_ENUM_STRUCT{Level, EntriesRead, Buffer} 之后，定长部分应当是 28 字节：ServerName 引用 / Level / EntriesRead / Buffer / 最大长度 / TotalEntries 引用 / ResumeHandle 引用。
应答解析只试 24 / 20 / 12 三个偏移定长部分是 20 字节，数组紧随其后。改成先试 20，并把解析失败时的前 8 字节打进错误信息——下次真机再失败，日志里能直接看出设备到底回了什么。
这条要记住的教训：「设备不支持」是个很舒服的结论，因为它把责任推给了对方。上一版就是在这里停下的，然后花时间写了一个 40 项的兜底名单去绕。真正的错误是一行编码顺序。以后凡是手写协议，先把报文逐字段对照 IDL 走一遍，再谈「设备不支持」。

14.3 播放中调出片库，要有明摆着的回头路

播放页一直有「片库」，但进了片库就回不去了——只能长按触发键，或者重新找到那一格再凝视一次。而「我就想看一眼片库、然后接着看」是高频动作。现在片库底栏有「返回播放」：播放器只是暂停、文件一直开着，所以这个动作只切屏 + 继续播，不重新打开文件、不丢进度。

14.4 成叠：832 部 104 页 → 9 叠 2 页

设计 08 章的三层是「柜子 → 叠 → 片」。之前只做了柜子和片，于是 832 部平铺成 104 页——用户原话是「噩梦」。这一刀把叠这一层补上，判据按内容形态取、不按协议取：

内容形态成叠判据叠的名字
网络共享里的片子按文件夹（Movies\2024、DCIM\100GOPRO）最后一级目录名 + 「N 部」
手机与相机拍的片子文件名里的拍摄日期（VID_20260712_143022）「7 月 12 日」+「N 部」
两种都分不出来不给叠，直接平铺—
为什么不给一个「成叠 / 平铺」的开关：多一个开关就多一次要理解的选择，而用户要的是「少翻页」，不是「学一个模式」。所以规则是自动的：部数 ≥24 且能分出 ≥3 叠时才成叠，否则老老实实平铺——多一层没意义的点击比多翻两页更烦。进了某一叠，底栏出现「← 全部叠」，返回时落回那一叠所在的页。

日期只从文件名里读。扫描期拿不到真实拍摄时间，而 mtime 记的是「入库时间」，用它分叠等于全部落在今天，反而更误导。

15 / V2.17 增补：名字的第三次修、子文件夹、同主机复用与横屏

alpha6 真机反馈：名字还是 IP（只多了「共享文件夹」几个字）；只输 IP 的设备依然不返回共享列表；加上六条改善建议与两处补充。这一章先说清「名字为什么第三次才可能修对」，再逐条处理入口与界面。

15.1 名字第三次修：不是解码，是节奏

第一次我以为是解码（ASCII → GBK），改完还是 IP。用户补了一句「PC 的共享也显示的是 IP」——PC 一定会应答 NBSTAT，这句把「设备的问题」彻底排除，问题必然在我的扫描方式里。
环节之前问题
时序254 个 IP 的端口探测与 NBSTAT 名字查询混在一起跑几十路并发 TCP 把无线电占满，350ms 的 UDP 名字查询不是迟到就是丢掉。名字查询被自己的端口扫描挤死了。
顺序扫到一个 IP 就顺手问名字改成分三阶段：先并行跑 mDNS（它要 2.5 秒，让它跟端口扫描重叠）、再 48 路并发连 445 只记 IP、等端口扫描彻底安静下来之后才一个一个问名字。
重试一次不回就放弃窗口 900ms，允许重试一次。无线丢一个包不该等于这台设备没有名字。
兜底只有 NBSTAT再加 NsdManager 的 _smb._tcp mDNS（实例名通常就是主机名）与 400ms 反向 DNS，三条独立路径取第一个成功的。
这一条要记住的教训：「名字显示成 IP」看起来是解析问题，实际是时序问题。同一个功能内部自己踩自己，比外部限制更隐蔽——因为每一段代码单独看都是对的。

15.2 共享列表：两种入参排布都发一次

V2.16 按 NDR 规则把报文重排成「28 字节定长 + 延迟数据」，这是标准写法。但 SHARE_ENUM_STRUCT 的联合体成员在 IDL 里带不带 [unique] 指针，各家实现的理解不完全一致，我没有真机能确认这台设备认哪一种。所以两种都发一次：错的那种只换来一个 fault，代价是一次往返，换来的是不必再猜。成功时写一条 RunLog（含变体号与共享数），下次真机日志里能直接看出它认的是哪一种。

15.3 子文件夹：默认扫，给用户一个「不扫」的开关

问题

「有的时候扫不出来文件」

旧的 MediaIndexer 只列起点那一层。用户把片子放在 Movies\2024\ 里，起点选 Movies，界面上就是空的——文件夹里明明有文件。

现在

默认递归，选项是「不扫描子文件夹」

BFS 往下走，两道闸：最多 300 个目录、20000 个条目。起点那一层列不出来必须报错（这是真失败），下层某个子文件夹没权限就跳过（这是常态）。选项文案按用户要求写成「不扫描子文件夹」，默认不勾——把选择权交出去，但默认给的是「能找到东西」。

这里有个容易搞错的边界：浏览只列一层，扫描才递归。选文件夹时如果也递归，整棵树会摊平成一屏，用户就没法一层层点进去了。

15.4 同 IP 加第二个文件夹，不该再输一遍凭证

用户要加 NAS\Movies 和 NAS\TV 两个片库，凭据是同一套。现在：点一台已连过的设备 → 自动用记住的凭证直接进文件夹浏览（连访客试连都省了）；手动添加时只要地址里的主机与某个已有片库相同、账号密码也一样，就直接复用那条 credentialRef，不再往凭据库里塞重复条目。

15.5 片库行：编辑、删除、隐藏

之前现在为什么
「改」「编辑」用户原话：「这两个按钮标签实在是太随便了」。单字动词省下的宽度，换来的是每次都要读一秒。
「删」「删除」同上。删除是破坏性动作，更不该用缩写。
只能删了重加「隐藏 / 显示」「临时不想在 VR 里看到这个片库」和「不要这个片库了」是两件事。隐藏只影响 VR 里的片库列表，索引与断点全部保留，标题压暗到 0.55 表示它还在、只是不出现。

另外补了一条用户没提但同一类的问题：编辑片库时换了文件夹，名字要跟着换。之前的实现里名字是独立字段，换了文件夹名字还停在上一个，列表里两个「Movies」指不同地方，确实混乱。现在的规则是：只在你没自己改过名字的时候跟着变——改过就尊重你的命名，不擅自覆盖。

写完这条之后回源码核对，抓到一个两个方向的死路：「哪些片库该显示」的查询接反了——配置页读的是只含未隐藏的那条，于是隐藏之后配置页也不显示它，用户再也没有地方把它显示回来；而 VR 读的是全部，所以隐藏对 VR 完全无效。两个查询各自都对，接反了就是「按钮按下去像在正常工作，实际上一边藏不住、一边回不来」。凡是有「开关」语义的字段，两端都要回源码确认读的是不是对方该读的那条。

15.6 横屏：按结构重排，不是拉伸

用户原话：「VR 使用的场景都是横屏，每次退出必须返回竖屏，体验很割裂，注意布局也要按横屏重排，不要简单拉伸一下敷衍了事。」

竖屏是一条长列：标题 → 两个入口 → 状态条 → 片库列表 → 手动添加 → 底栏。横屏最缺的是高度、最富余的是宽度，所以不是把这一列拉宽，而是拆成上下 + 左右：

区域竖屏横屏
顶部大标题 + 副标题占掉三行一条窄带：品牌 + 副标题 + 日志 + 进入 VR，三样收进一行
主体一列到底，靠滚动看完全部左右两栏：左栏「先做什么」（两个大入口 + 四态状态条），右栏「已经有什么」（片库列表 + 手动添加）
滚动整页一个滚动两栏各自独立滚动——片库多了不会把左栏的入口顶走
文案「运行日志 · 出问题请截图给我」「放入纸盒，进入 VR」values-land 覆盖成「运行日志」「进入 VR」——横屏顶栏是图标位，不是说明文字

实现上两套 layout 的 view id 完全一致（25 个对 25 个，差集为空），ActivitySetupBinding 一行都不用改；configChanges 接管方向变化，旋转时 Activity 不重建，正在填的表单、正在跑的扫描都不会被打断。

① 以上全部没有真机验证——名字的第三次修、srvsvc 两种排布、递归扫描、凭证复用、隐藏/显示、横屏版式，都只经过静态校验（53 Kotlin / 9,782 行 / 25 对 id 一致）、真实编译与离屏推演；② 横屏只做了配置页，对话框（编辑片库、选文件夹）没有横屏变体，横屏下打开会是竖屏比例居中；③ 隐藏的片库在 VR 里不出现，但「换柜子」整层还没做（B2），所以「临时藏起来」目前只能靠退出 VR 改配置；④ 子文件夹扫描是单次深度优先展开，不做增量——改了远端目录要手动重扫。

16.1 横屏为什么「只是拉伸」

用户原话：「横屏完全没有重排，就只是简单拉伸了一下。」——上一版我确实写了 layout-land，两栏、独立滚动、短文案全都做了，但它根本没被用上。
环节上一版结果
manifest加了 configChanges="orientation|screenSize"，本意是旋转时不重建、别把正在填的表单弄丢方向变化时 Activity 不重建
布局切换setContentView 只在 onCreate 里调过一次横过来仍然是竖屏那套 layout，被横向拉宽——写好的 layout-land 一次都没加载

修法：在 onConfigurationChanged 里自己重新 inflate 一套（系统这时才会按 layout-land 取资源）、重新绑视图、按当前数据重画一次；表单里已经填的内容按 id 搬过去，不丢输入。视图绑定抽成 bindViews()——漏掉任何一个，横屏下那个按钮就是死的。

教训：「旋转不重建」是个好目标，但它和「按方向换布局」是两件事。加了 configChanges 就等于自己接管方向变化的全部后果，包括换布局。只加 configChanges 不写 onConfigurationChanged，等于既没重建、也没换布局。

16.2 断点为什么丢了

用户看到的是「隐藏之后再显示回来，断点没了」，于是以为是隐藏的锅。回源码核对：隐藏只改 enabled 一列，不碰断点。真正的原因在更下面——

表上一版问题
media_item主键是自增 id改递归范围、换文件夹、重扫时行会被删掉重插，自增 id 就变了
play_progress主键是 media_id，外挂在那串 id 上id 一变，断点全成孤儿。用户攒了几十个小时的进度，被一次「改个扫描范围」清空。

修法：断点主键改成 media_key = sourceId:path——路径是稳定的。同时 purgeMedia() 不再删断点，只有真正删除片库才连断点一起清。数据库 2→3 的迁移用 media_item 把旧 media_id 翻译成路径接续过来，升级一次不会清掉已有断点。

16.3 「要完全退出 App 重开才能扫描」

用户原话：「取消勾选之后提示扫描不成功，要完全退出 APP 再重新打开才能扫描成功。」——「重开就好」这四个字指向内存或连接，不是网络。

查到的是连接泄漏：VrActivity.boot() 里的 SmbSessionPool 是局部变量，onDestroy 够不着它，于是每进一次 VR 就在 NAS 上留下一条没关的 SMB 会话。进出几次之后，设备那边的并发连接被占满，配置页再扫描就连不上——而重启 App 会把所有连接放掉，所以「重开就好了」。

修法：池子提升为字段，onDestroy 里 close()；配置页退出时也关；SmbSessionPool 补一个 public close()（原来只有「连接看起来坏了」才走的 invalidate()）。另外把扫描失败的具体原因写进运行日志并在界面上指路——上一版只说「扫描没成功」，用户除了重启没有第二条路可走。

16.4 加片库的入口，和整行可点

用户原话：「加第二个文件夹根本不知道怎么操作，点现有的片库也完全没有反应。」
入口

「＋ 加片库」和已有片库放在一起

原来唯一的入口是列表下面的「手动添加」折叠区——位置在片库之后，文案又像设置项。现在「我的片库」标题行右侧直接一个「＋ 加片库」，点开把手动区展开、焦点落在地址格。

整行

点卡片就是编辑

原来只有右下角那个 12sp 的「编辑」小字能点，卡片本身是死的。用户想「在同一台设备上再选一个文件夹」，第一反应就是点那张卡片——现在点了就进编辑。

16.5 隐藏按钮和别的按钮叠在一起

两个原因一起改：卡片根布局原来没有 padding，按钮行直接贴着卡片右边缘；「隐藏」与「编辑」之间又没有 marginStart，两块带底色的按钮紧挨着，看起来就是叠着的。现在统一 14dp 内边距 + 每个按钮 8dp 间距，四个按钮等宽 52dp。

16.6 「叠」改成「集合」

用户原话：「还有『叠』改成『集合』，不要用些奇奇怪怪的名称。」

全部用户可见文案改掉：标题里的「N 个集合」、底栏的「← 全部集合」、提示里的「凝视一个集合即进入」。内部代码里的 MediaStack / StackBuilder 不动——那是实现，不是用户读到的字。产品里的词必须是人话，代码里的词只要准确就行。

16.7 名字的第四条路，与共享列表的出路

PC 名字

Windows 默认不应答 137

两台 NAS 名字对了、PC 还是 IP。原因很具体：Windows 关着「网络发现」时不应答 NBSTAT（137/UDP），mDNS 里也不注册 _smb._tcp，家用路由器又常常没有 PTR。三条路全断。但 445 是开着的——那就顺着这条已经通了的路问它自己：srvsvc 的 NetrWkstaGetInfo（opnum 6），wki100_computername 就是「网络」里那个名字。放在最后才试，只有前面全失败才多花一次连接。

共享列表

枚举失败时给一条不用记语法的出路

只输 IP 的设备仍然不回报共享列表。这一版把 srvsvc 每一步（绑定 / 请求 / 解析）的失败原因都写进运行日志，并在界面上直说：「要么它要账号，要么它不允许程序枚举共享（Windows 常见）。把地址写成 IP/共享名 就能直接连——共享名在设备管理界面里能看到。」共享名不是机器的语法，是用户看得见的名字；分隔符由程序补。

位置做法为什么

17 / V2.19 增补：把「正前方」真的交给脖子，把预览图真的给一张画面

这一版做两件之前一直写着「设计」的事（B4 姿态闭环、B5 舒适俯角），并回头修两条 alpha8 真机反馈里最扎人的：横屏粗糙、预览图敷衍。过程中推翻了一个我自己的前提——B5 原来的写法会让界面单独飞走、画面留在原地，那不是舒适，是更别扭。

17.1 姿态闭环：为什么必须先问再动

3DOF 只有手机姿态。它分不清「整个人躺下了」和「头相对身体抬起来了」。看 360 内容时长时间抬头就是常态——任何「重力偏离 + 稳定时长就自动重定」的判据，都会把用户正在看的那一段抢走。
环节判据为什么是这个数
死区偏离 40°正常转头、抬头看画面顶部都在 40° 以内；低于这个值会天天误报
抖动容忍8°手抖、呼吸、纸盒松动都在这个量级以下
稳定时长1.5 秒够长到「真的躺下去了」，够短到不用干等
候选寿命6 秒没人理就自己收起，绝不常驻挡画面
缓转0.8 秒瞬跳会晕，太长像卡住
落定静默0.6 秒缓转期间参考系在动、`pitch` 一路回到 0；不静默就会拿残差当场再弹一次确认

确认浮层只有两个目标：「挪到这里」与「不用了」，外加一条剩余时间细条。这一层是打断，打断上不该再摆一排按钮。它出现时会把下层目标全部清掉，凝视不可能穿过浮层打到片库卡片上。

17.2 缓转不是调 recenter()

上一版我在表里写「凝视一次才 0.8s 缓转」，但代码层面 recenter() 是瞬跳：inverseOffset 从旧值直接变成新值，整个视界在一帧里平移几十度。那是头显里最典型的晕动触发源。

做法结果
对两个旋转矩阵逐元素线性插值错。插出来的矩阵不再正交，画面会被拉斜、剪切
转四元数 → 球面插值 → 转回矩阵正确。同号取短弧（q 与 -q 是同一个旋转，取错会绕远路转 360°）

关键落点：headRotation() 被三处调用——视图矩阵、凝视落点、手势识别。三处都必须走同一个 offsetNow()，否则缓转那 0.8 秒里画面在动、准星已经跳到终点，用户看到的是一个乱飞的圈。

教训：「缓转」这种词很容易在设计稿里活下来、在代码里死掉。一个动词只要涉及时间，就必须问一句：这 0.8 秒里，中间那些帧长什么样？

17.3 舒适俯角：我的前提是错的

B5 原来写的是「把 uiQuad(-0.46f) 写死的 −13° 改成随 comfortPitch 缓动的平面偏移」。听起来很对，做下去才发现：它只挪 UI 平面，视频留在原地。
方案躺下之后结论
把 UI 平面按 comfortPitch 往上挪片库飘到脸上，画面还挂在天花板前面，用户仍要仰头找片作废。UI 与视频分家，比不动更别扭
缓转整个参考系视频 / UI / 字幕 / 准星作为一个整体转过去采用。「天花板影院」这个说法只有在整体转的前提下才成立

于是俯角只剩一条相对规则：控制台比「正前方」低 13°。参考系换了，这条规则自动成立，不需要任何补偿。相应地 VrUiState.comfortPitch 整个删掉——留着一个不参与渲染的字段，下次一定有人拿它去乘矩阵，然后再一次把界面和画面拆开。

17.4 确认浮层会被自己的准星点掉

这是个只在真实时序里才看得见的问题。浮层出现在画面正中，而准星本来就停在画面正中——「挪到这里」正好在准星底下。凝视停留 1.5 秒，确认就被点掉了，用户什么都没做，画面自己转了。

修法不在浮层里，在凝视检测器里：GazeDetector 的「换屏键」必须把 postureCandidate != null 算进去，让浮层出现算一次换屏，走那条「必须先离开再回来」的规则。任何新浮层都要检查这一条——这是 V2.9 上膛机制留下的通用保险，不是这一个浮层的特例。

17.5 预览图为什么「太敷衍」

用户原话：「片库的预览图真是难尽，也太敷衍了。」回源码核对，比「不好看」严重得多：它没有信息。
上一版结果
没有同名图片时，生成一张渐变封面，中间放文件名首字母片库绝大多数是 VID_20260712_143022.mp4，首字母全是 V。八格片库是八张一模一样的「V」
「八个格子长得一样」等于没有格子。用户在一堆都拍同一个房间的片段里，靠的正是时刻
现在做法
本地视频真抽一帧。MediaMetadataRetriever.setDataSource(context, uri) 能直接读 content://，不需要 fd、不用把文件读进来。取 1 秒处的关键帧——相机片段开头常是黑场或镜头盖。铺满后居中裁切，不拉伸
抽不到时生成带身份的封面：色相按文件名散列（相邻两条颜色不同）、中间是时刻、上面日期、下面时长，右下角一个小播放三角。不画首字母
有画面之后底部压一条透明到黑的渐变压条，补回「日期 + 时刻」与时长。有画面不该比没画面信息更少
旧封面文件名带代际号 g2。改生成规则必须进位，否则用户手机上那批「一个 V」永远不刷新

网络片源仍然只能生成封面：SMB / WebDAV 只有自定义 DataSource，没有可交给 MediaMetadataRetriever 的 fd，整段拉流会在前台播放时抢带宽。这条限制写在 PosterRepository 的类注释里，不是遗漏。

17.6 横屏：同一套语言的另一种排法

用户原话：「横过来已经是两栏了，但老实说，横屏界面很粗糙，给人一种很乱的感觉，和竖屏的设计语言也不一样。」——上一版只做了「摆位置」，没做「统一语言」。
位置上一版横屏现在

主张句整个删掉，横屏看起来像另一个 App 的列表页保留，29sp 收到 22sp，加回 kicker
